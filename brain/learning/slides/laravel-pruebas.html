Un guardia que repite tu prueba

Probar a mano demuestra que el rango funciona hoy, en tu computador. No dice nada de mañana.

Una prueba automática es como el guardia de la portería: revisa lo mismo cada vez que alguien entra. El CI la corre en cada MR, y si alguien vuelve a dejar el filtro de un solo día, el pipeline se pone rojo antes de llegar a desa.

Regla Toda corrección lleva una prueba que falle sin ella. Si nunca la viste fallar, no está verificada: solo está escrita.

Glosario primero

TérminoQué es
Prueba de FeatureHace una petición HTTP de verdad a la aplicación (sin navegador) y revisa la respuesta
FactoryFábrica de registros válidos con datos inventados. Tú fijas solo lo que le importa al escenario
RefreshDatabaseCada prueba arranca con la base de pruebas vacía; lo que creó se revierte al terminar
setUp()Se ejecuta antes de cada prueba: aquí se crea el usuario y se inicia sesión con actingAs
Afirmación (assert)La comprobación: si no se cumple, la prueba falla y dice por qué

Las tres partes de toda prueba

Prepararfactories crean el escenario
Actuar$this->get(...)
AfirmarassertContains / assertNotContains
Avanza para recorrerlo.

WithoutMiddleware salta el permiso: aquí no se prueba el permiso, se prueba la consulta. El mensaje al final de cada assert es lo que leerás cuando falle.

La trampa de este repo

DispatchFactory crea una empresa, un servicio y un centro operativo nuevos por cada despacho.

Así falla

$base = DispatchFactory::new()->create([...]);
$ayer = DispatchFactory::new()->create([
    'start_datetime' => '2026-11-11 22:00:00',
]);

$ayer queda en otro centro: el filtro de centros del usuario lo saca y la prueba falla por una razón que no es la fecha.

Así sí

$same = [
  'company_id' => $base->company_id,
  'operational_center_id' => $base->operational_center_id,
];
$ayer = DispatchFactory::new()->create(
  $same + ['start_datetime' => '2026-11-11 22:00:00']
);

Y el usuario necesita ese centro: UserOperationalCenter::insert, igual que el modelo.

Errores típicos

Solo el caso feliz

Afirmar lo que sale, nunca lo que no sale. Una consulta sin filtro también pasa.

Datos que no aíslan

Si el de ayer es además de otro servicio, no sabes si salió por la fecha o por el servicio.

No verla fallar

Devuelve el whereDate de un día y corre la prueba. Si sigue en verde, no prueba nada.

Nombres largos

Máximo 5 palabras sin test_. El detalle va al docblock.

No copies del modelo los comentarios sueltos dentro de los métodos: en código nuevo no van.

Preguntas de cierre

1. Si tu prueba pasa con el código viejo, ¿qué te está diciendo?
Que no prueba la regla nueva: el escenario no tiene un registro que solo el rango deje entrar (el del día anterior o el del posterior).
2. ¿Por qué el despacho del día anterior debe ser del mismo centro y servicio que el base?
Para que lo único distinto sea la fecha. Si cambia otra cosa, cuando falle no sabrás cuál de las dos lo sacó.
3. ¿Qué parte del escenario demuestra que la Distribución de pesos no cambió?
Una segunda prueba que llame sin dispatch_date, con start_datetime y service_id como la Distribución, y afirme que solo sale el mismo día y servicio.

Ahora tú

1. Responde las tres preguntas antes de mirar las respuestas.

2. Escribe en una tabla el escenario: qué despachos creas, qué cambia cada uno respecto al base y si debe salir o no.
